# 变更记录

本文件记录 `dsh-voice-mode-desktop` 的改动过程，按"在做什么的时候撞上什么"组织，便于同版本环境复现与排查。

第一次适配在 2026-09-30 ~ 10-01 完成，目标环境：Windows + DSH NEXT 桌面版 `2.0.17-next`（内部 `@deepseek-ai/* 0.2.0-rc.2`）。

---

## 未发布（2026-10-26）

- 修「语音归属为空导致整段不朗读」：模型流进来时如果当前语音会话为空，首条流自动接管（日志 `adopt stream`），不再依赖设置面板里的语音开关去设置归属；同一时刻只有一个会话朗读的约束不变。
- 合成失败留痕：连续三次失败或引擎返回空音频时，日志写一行 `tts skip`，带引擎名、引擎状态、失败原因和原文前 40 字；`tts-skip` 事件增加 `reason` 字段，界面提示能带上原因，不再只是静默跳过。
- 新增 `docs/smart-app-control.md`：Windows 智能应用控制（SAC）拦截 Python 运行时里未签名 `.pyd` 的诊断与放行做法——如何用补充策略按路径放行、怎么验证、怎么撤销，以及为什么不去关 SAC。文档已脱敏，不含本机路径与证书信息。

## 0.1.8（2026-10-20）

- 修状态条波形冻在旧值上：波形只认最近 250ms 内真正更新过的电平，空闲或播放时归零/衰减，不再把最后一帧的满格数组一直画下去。
- 手动抢话模式下没按住时不把音频送进识别，同时把电平归零；播放中电平直接输出 0，界面不再显示播放时的假波形。
- 长按启动语音时若正在朗读，立即打断（此前只在手动模式和特定按键路径下生效）。
- 诊断：新增每秒一次的 audio-level 与 ui-level 打点，排电平/波形问题时能直接看现象。

## 0.1.7（2026-10-18）

- 识别引擎下拉真的能切了：新增 readAsrEngine / applyAsrEngine，面板、设置接口和工具走同一条切换路径；档位落盘到 %LOCALAPPDATA%\dsh-voice-mode\settings.json，重启后恢复。
- 重启职责拆到独立插件 @nutshelllee/dsh-agent-restart：语音插件只保留语音，启动时读 voice-resume.json 决定是否自动开语音。
- 重启后的续跑由 agent-restart 完成：应用就绪后 5 秒排一条来源为 restart 的消息开新回合；只排一次，不建目标、不标完成。
- 文档：docs/restart-design.md 记录重启机制的调研、取舍和验收标准。

## 1. 踩坑现场

| 当时在做的事 | 撞上的现象 | 根因 | 依据 |
|---|---|---|---|
| 把插件装进桌面版 profile、首次重启 | 插件持续 `failed to import` | 先用裸包名挂载第三方 profile 插件，在 0.2 下解析不到；随后发现依赖 `msedge-tts` 里的 `require("buffer/index")` 在 Electron 的 Node 模式下解析失败（`createRequire(...).resolve.paths` 对子路径返回空） | 宿主启动日志 + 独立复现脚本 |
| 插件刚能导入 | 桌面版进入 recovery，界面起不来 | 客户端服务 `settingsScope` 自 0.1.7-rc.1 起被移除，插件仍在 `inject` 中声明它；桌面版把"有 entry 未激活"当作致命错误 | 应用诊断 JSON：`runtime.phase=recovery`、`pending (waiting for service: settingsScope)` |
| 希望插件的配置项可见可改 | 插件列表里能看到，点进去是空的、无法修改 | 0.2 的插件配置表单只渲染 schema 中标了 `volatile` 的字段，而插件一个都没标 | schema 投影试验：未标时投影为空，标注后得到 `rate`/`mode` |
| 在设置里寻找配置入口 | 设置中没有对应页面 | 渲染插件配置表单的页面（`dsh-client-ui-plugin-manager`）在该部署中未挂载；第三方市场页也不提供配置入口 | 逐包核查设置区注册的页面列表 |
| 用户报告"朗读没有声音" | 日志中每次模型流都记录 `voice=null`（跳过朗读） | 朗读触发要求"模型流的会话号等于当前语音会话号"，而当时语音会话为空 | 宿主日志时间线比对 |

同批发现的两条属于其他插件，不在本仓库范围：默认搜索后端按模型调用计费；某个清理插件自身依赖未安装完整导致导入失败。

修掉的这两个漏点（先由日志判定，再动代码）：

1. **覆盖**：`engine.onSegment` 原来用渲染期快照 `draftRef.current` 做"读—改—写"再 `setDraft` 覆盖整段。快照只在界面重画时刷新，两段识别在同一个渲染窗口内落地时，后一段用陈旧的前值拼串，把前一段覆盖掉。现在写入交给宿主的 `insertText(text, span)`：位置来自 `captureInsertion()` 的实时取点，草稿版本号对不上时它返回失败而不是覆盖；失败就留在队首重试（每 150ms 一次，直到成功），绝不静默丢字，也不覆盖用户选中的内容。
2. **丢弃**：`finalizeSegment` 里 `segmentEpoch !== epochSnapshot + 1` 的两处守卫，会在"这段的响应回来时已经开始了新的一段"时把整段已识别文字丢掉（22:34 那次正是如此）。现在段在定稿开始时"开"、拿到文字或确认拿不到时"合"，输入框侧按段号升序排队：更早的段没落地就压住后面的，落地顺序永远与说话顺序一致；再加 30 秒超时兜底，防异常路径把队列卡死。
3. 顺带把 `submitDraftNow` 的落地闸门补上：队列没清空就不发消息，避免把半截话自动发出去。

宿主那条写入接口（`inputActions.captureInsertion()` / `insertText(text, span)`）与官方 `dsh-experimental-client-ui-voice-input` 用的是同一条，语义为"插在取点处、冲突即拒绝"。`insertText`/`captureInsertion` 不存在时会退回旧的整段覆盖写法，保证老版本宿主仍可用。

## 3. 被否决或回退的做法

- **裸包名挂载第三方 profile 插件**：在 0.2 下导入失败，改为 bundle patch 挂载本包。
- **"会话号不一致也朗读"的放宽**：无证据支撑（改动前朗读可用），已回退，仅保留一行诊断日志。
- **在读取点叠加两层速率/音色校验**：与入口解包重复，已删除。
- **依赖宿主官方插件配置表单**：该页面在此部署未挂载，路线作废，改为自带设置页。

## 4. 维护契约

1. **改动集中在 `lib/` 的两个文件**：`index.js`（host 半体：schema、设置端点、诊断日志）与 `client.js`（客户端半体：inject、设置页、字幕与状态条）。
2. **每条改动都能指到一次失败**：新增改动前先确认现象与日志；删除某条改动应当重新出现对应失败。
3. **`msedge-tts` 的补丁不进本仓库**：它是依赖包的本地修改，由 `scripts/fix-msedge.mjs` 在安装后处理。
4. **升级上游**：合并新版本时，对照本文件逐条确认改动是否仍需要（上游若已官方支持 0.2，对应改动可移除）。

## 5. 本地朗读换模型：vits 从 zh-ll 换成 piper 中文中档（2026-10-14）

| 当时在做的事 | 撞上的现象 | 根因 | 依据 |
|---|---|---|---|
| 微软 Edge 朗读接口开始按地区拒绝老握手，切回本地引擎 | kokoro 一句要 2~4 秒，用户直接判"太慢" | kokoro 走原生 addon 且模型大（约 160MB），在这台机器上实测 0.9~1.05 倍实时，基本等于"读一句等一句" | 本机实测：kokoro int8 2.3 秒音频要 2.0~2.3 秒算完 |
| 想改用插件内置的 vits | 那个模型英文单词整段丢掉 | 默认模型 `sherpa-onnx-vits-zh-ll` 是纯中文词表，遇到 opencode/dsh 这类词直接 `Ignore OOV`；而且它本身约 1.1 倍实时，比 kokoro 还慢 | 日志逐条 `Ignore OOV 'OpenCode'`；实测 1.10 倍实时 |
| 换 piper 中文中档（60MB）+ espeak 音素库 | 实测一句话 0.25~0.4 秒，中英都读得出来 | piper 用 espeak 音素化，不查中文词表，所以英文按英文规则读，不会丢 | 本机实测 0.15~0.24 倍实时；同一句英文句子的音频时长从 1.3 秒（丢词）变成 2.2 秒（正常读出） |

改动落在两个文件：

## 9. Edge TTS 修回来了：Sec-MS-GEC v2 令牌（2026-10-14）

用户的原话："我希望在插件那里我可以自己换不同模型，比如换回 Edge TTS 的话，你就把那个令牌适配回来。"

**病因**：微软把 Edge 朗读端点迁到了 v2 票据。老算法是
`SHA256(五分钟窗口的 Windows 时间戳 + TrustedClientToken)`，返回一坨 64 位十六进制；
v2 换成了 `"<16 位 CS64>-<64 位 SHA256>"`，并且请求头里的
`Sec-MS-GEC-Version` 必须从 `1-…` 改成 `2-…`。两者都对不上就握手 403。

**改法**：

- 新增 `lib/gec-v2.js`：把 rany2/edge-tts 7.3.0（PR #492）里那段算法**逐行**移植成 JS。
  算法本体是一个换过常量的 SHA-256（自定义 IV、自定义消息扩展、第 15 个轮常量被替换、
  两个 sigma 有额外 XOR 调整）加一个自制的 CS64 校验和。JS 侧用 BigInt 实现，避免 32 位溢出。
- `lib/edge-tts.js`：`GEC_VERSION` 改成 `2-143.0.3650.96`，`secMsGec()` 改成调用 v2 实现。
  合成 URL 和列音色 URL 两处都走同一个函数，一起升级。
- 备份：`lib/edge-tts.js.bak-edgev2-20261014`。

**正确性验证**（这一步很关键，不是靠猜）：

1. 用本地 Python 3.10 加载上游原始 `drm.py`，对 4 个固定时间戳（含小数）算出参考令牌；
2. 用同一批时间戳跑 JS 移植版；
3. **4/4 逐字符一致**，当前时刻的令牌形如 `4AE0CEDE82076AFF-6DB783FAB…`。
4. 端到端：走插件自己的 `synthesize()` 真连微软服务器，返回 21024 字节 MP3，
   文件头 `ff f3`（合法 MP3），耗时 1480 ms。

**弯路记录**：一开始改错了地方——把补丁打到了 pnpm store 里的 `msedge-tts` 包上，
但插件有自己写的 `lib/edge-tts.js`（注释里写明"carries no third-party TTS wrapper"），
根本没依赖那个包。改完才发现，已还原，store 保持干净。**下次改这块钱先 grep 一下 `SYNTH_URL`。**

  主动把自己杀掉再抛错，不留孤儿进程。

改完语法校验通过，需要再重启一次 DSH 才生效（这次重启之后应该只有一个 worker）。

### 14.4 找到"假装在说话"的真凶：stdin 编码（2026-10-15）

用户反馈：worker 合成出来的三条（含速度 1.0 那条）全是乱码，"假装在说话，语气对、发音全错"。

**排查手段**：用插件自己的 SenseVoice（`lib/sense-worker.mjs`）把音频转回文字，客观对比。
同一个文本"先看一下现象，再决定怎么处理。"：

| 来源 | 识别结果 |
| --- | --- |
| 官方 CLI 输出 | "先看一下现象，再决定怎么处理。" ✓ |
| 我们的 worker 输出（修复前） | "为保练君如邦仆任宗熬玉月冬同千缠童折磨。" ✗ |

**根因**：Windows 上 Python 的 `sys.stdin` 默认按系统编码（cp936/GBK）解码，而插件送进来的是 UTF-8。
中文文本被解成乱码，模型拿到的就是乱码音素 —— 所以"语气对、发音全错"。
CLI 那条没问题，是因为它的文本走 argv（Windows 上是 UTF-16），不经过 stdin。

**修法**：worker 一开头把三个标准流都强制成 UTF-8：

```python
for _stream in (sys.stdin, sys.stdout, sys.stderr):
    _stream.reconfigure(encoding="utf-8", errors="replace")
```

修完复测：worker 输出被识别成"先看一下现象，再决定怎么处理。"，与 CLI 一致。

**顺带量清楚语速**（修复前测的时长不可信，这次重测并逐条识别）：

| 速度 | 时长 | 识别结果 |
| --- | --- | --- |
| 1.0 | 6.40 秒 | 基本逐字正确 ✓ |
| 2.0 | 3.04 秒 | 开始丢字："人肉跟磕磕可可" |
| 3.0 | 2.06 秒 | 完全不可懂 |

所以引擎里把 ZipVoice 的语速**封顶到 1.3**（界面滑块再往上拖也不会把话压坏），
配置里的 rate 从 3 降到 1.2。

### 14.8 常驻进程的显存缓存要还回去（2026-10-15）

分段测出来的账很清楚：

- 模型加载完：reserved 0.53G，allocated 0.51G —— 权重其实只有半 G。

### 14.13 上限放开到 2.0（2026-10-15）
